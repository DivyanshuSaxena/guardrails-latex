\section{Guardrails}\label{sec:guardrails}
 
To address these issues, we propose \textbf{Guardrails}, a systematic, uniform approach to specify and enforce constraints on learned models in OS. 
Guardrails serve as an always-on safety net, preventing the learned policy from making unbounded errors and giving OS developers confidence in deploying such policies in production environments.

\subsection{Overview}
At its core, a guardrail background service runs in a ``learned-enabled'' OS. OS developers specify guardrail rules for each learned component being deployed.

Each guardrail rule has two primary components:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Properties (Section \ref{sec:property}):} Declarative expressions of desired behaviors and constraints. Properties capture the guarantees OS developers require, such as performance bounds, resource constraints, or safety invariants.
    \item \textbf{Actions (Section \ref{sec:action}):} Corrective measures automatically invoked upon detecting property violation.
\end{enumerate}
At runtime, the guardrail service monitors relevant metrics specified in the guardrail rules (e.g., inference latency, CPU usage, error rates), evaluates them against the specified properties, and triggers the associated actions if needed. 
Through these well-defined rules, guardrails limit risk by detecting policy misbehavior in real time and responding automatically.

\subsection{Properties}
\label{sec:property}

Properties describe the criteria under which a learned policy is considered ``safe enough’’ for OS. 
These constraints can be expressed over (i) the \textit{input state} of a model (e.g., the distribution of requests), (ii) the \textit{model’s output} (e.g., predicted values or discrete decisions), or (iii) the \textit{resulting system behavior} (e.g., resource usage, latency, throughput). \mike{Make sure we have examples for all three catgories, and label the examples with their category}

With consultation from domain experts, we summarize some common system properties that can be generally desired for all learned OS policies.

\paragraph{In-Distribution Data.}
A model that was trained on a certain workload distribution may fail on unseen or drastically different inputs. \jane{cite} It is hard to collect a diverse enough training dataset. Hence, one primary property for learned models is that \textit{runtime inputs remain in-distribution}. 
If the guardrail service detects a dramatic shift, it flags a violation. 
For example, \textit{LinnOS}~\cite{linnOS-osdi-20} uses supervised learning to predict SSD I/O times; if the observed I/O metadata diverges beyond a specified threshold from training conditions, the guardrail can trigger a violation.
This prevents large performance regressions when the workload changes abruptly. \mike{What about also checking feasible values on output here as well, e.g. not allowing read-ahead of 2gb? Or where does that go?}

\paragraph{Robustness to Small Perturbations.}
OS often deals with noisy signals and measurement errors (e.g., hardware counters).\jane{cite} 
A robust model should not drastically alter its decisions with minor input perturbations. 
Hence, a guardrail can check whether similar inputs yield approximately similar outputs and similar system behavior over a time window. 
For LinnOS, two I/O requests of similar block offset, size and read/write type should lead to latency predictions in a similar range.
For KML I/O readahead prediction, similar page access patterns should yield similar readahead value decisions as well as similar I/O throughput.

\paragraph{Lightweight Decision-Making.}
High inference latency for learned models in the OS layer may take back any performance benefits of learned policies. 
To address this, a guardrail can track and constrain the system's decision-making time. It could either be the learned model's inference time (e.g., 10~$\mu$s for latency prediction in LinnOS), or a learning-aided controller's decision time (e.g. \jane{??} for cwnd change in Orca~\cite{orca-sigcomm-20}).
This ensures that machine learning overhead does not dominate or violate real-time constraints in critical OS paths.

\subsection{Actions}
\label{sec:action}

When a guardrail property is violated, the OS must have a well-defined response. 
We categorize these \textbf{actions} into three classes:

\begin{enumerate}[leftmargin=*]

    \item \textbf{Verbose Logging.}
    The cause of property violations may be hard to track, especially given the black box nature of machine learning models. The guardrail may activate a verbose logging mode. In this mode, the system captures richer diagnostic traces, such as extended features, model intermediate outputs and related kernel events - which are too expensive to be always-on when error-free. This on-demand extra context can help pinpoint the root cause of misbehavior by revealing both system and model logic. When system returns to stable operation, verbose logging can be automatically reverted back to regular logging.

    \item \textbf{Fallback to a Baseline Policy.}
    For system components with a classical heuristic that can meet the guardrail properties, the OS can always revert to this preexisting heuristic when the learned model violates any of the properties. 
    This ensures system's smooth operations when learned policies fall short. 
    A typical example is when Orca fails under extreme or unexpected workloads~\cite{yang2024c3}; the guardrail can revert to the kernel’s default congestion control algorithm.

    \item \textbf{Model Retraining.}
    In some scenarios (e.g., when in-distribution data is violated), the learned policy model needs to trigger retraining to update with new observations. 
    This action protects the OS from long-term harm caused by an unfit model.
