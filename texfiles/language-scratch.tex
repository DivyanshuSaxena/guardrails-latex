\section{\lang: Guardrail Description Language}\label{sec:gdl}

We present the \emph{Guardrails Description Language} (GDL), a declarative language for specifying performance guardrails over kernel behavior.

Concretely, a guardrail specifies: (i) \emph{when} it is evaluated, (ii) \emph{what condition} must hold on the portion of execution it inspects, and (iii) \emph{what corrective action} is applied when that condition fails.

\subsection{Formal Definition of Guardrails}

We consider the application of a guardrail to a policy $\policy$ in system $S$ (where the system could be the OS as a whole, or a specific subsystem that the policy under evaluation is a part of).
Each policy is assumed to be parameterized, where the parameter denotes different implementations of achieving the same policy. 
By `policy', we mean the high-level objective of the policy, not the exact implementation, e.g., hugepage management is the policy, while Linux and CBMM are the parameters. 
Let $\states$ denote the set of possible system states for $S$ (including various statistics and state of in-kernel objects) and say $\policies$ is the set of alternate policies that can be deployed in the system (at a time, exactly one of these policies $\policy \in \policies$ runs in $S$). We will now formally describe how a guardrail operates in this system.

A guardrail $G \in \guardrails$ in a system $S$ (as defined above) is given by the tuple $(\condition{},\action{})$ where $\condition{}:\states^*\xrightarrow{}\{{\sf true},{\sf false}\}$ is a performance property over a bounded history of system states and $\action{}: \Pi\xrightarrow{}\Pi$ is a corrective action that \sujay{modifies the policy or} switches between policies.

Thus, the guardrail specifies that the performance property $\condition{}$ should hold for the system, and if it does not hold, the guardrail specifies the action $\action{}$, resulting in an update to the deployed policy.
Formally, we write $\guard{G}{\sigma}{\policy}{\policy'}$ to denote that the guardrail $G$ specifies an update in the deployed policy from $\policy\xrightarrow{}\policy'$ when it observes a sequence of system states $\sigma \in \states^k$. The semantics for this is defined as:

}{

}\quad
\inferrule[Guard-Violation]{
    % G=(\condition{},\action{}) \quad 
    \condition{}(\sigma)={\sf false}
}{
    \guard{(\condition{},\action{})}{\sigma}{\policy}{\action{}(\policy)}
}
\end{mathpar}

\paragraph{Runtime monitors for guardrails.}
In principle, guardrails as defined above apply to every sequence of states $\sigma$ that a system may observe.
However, there is a cost associated with evaluating the performance condition $\condition{g}$ -- storing the relevant system states in $\sigma$ in the kernel at all times, reading them when evaluating the property, etc., imposes a computational as well as storage cost. 
Thus, in practice, the evaluation of guardrails must be restricted to a small set of `useful' points where the performance condition is likely to be violated.
Additionally, alternate policies for the same task may warrant different types of guardrails.
For example, a hugepage promotion policy based on offline cost-benefit profiling~\cite{cbmm-atc22} may require two guardrails: one for tracking whether the offline-profiled benefits are still accurate at run-time, and another for checking if the overall policy is resulting in useful promotions.

Both of these requirements are met by runtime guardrail monitors.
Formally, a runtime monitor $M$ is a tuple $(G, \trigger{}, \enabledMap)$ where $G$ is the guardrail that $M$ is monitoring, $\trigger{}:\states^k\xrightarrow{}\{{\sf true},{\sf false}\}$ is a function that checks whether a given sequence of system states meets the requirement for `triggering' the guardrail evaluation, and $\enabledMap:\policies\xrightarrow{}\{{\sf true},{\sf false}\}$ is a mapping from policies to a boolean that states whether the monitor $M$ should be enabled for the policy $\policy \in \policies$.
We write $\monitor{M}{\sigma}{\policy}{\policy'}$ to denote that when a monitor $M$ observes the execution sequence $\sigma$ for a system under policy $\policy$, the resulting outcome is the update of policy to $\policy'$. These semantics are defined as:
\begin{mathpar}
\inferrule[Not-Triggered]{ 
    % M=(G,\trigger{},\enabledMap) \quad
    \trigger{}(\sigma)={\sf false}
}{
  \monitor{(G,\trigger{},\enabledMap)}{\sigma}{\policy}{\policy}
}\quad
\inferrule[Not-Enabled]{
    % M=(G,\trigger{},\enabledMap) \quad
    \enabledMap(\policy)={\sf false}
}{
  \monitor{(G,\trigger{},\enabledMap)}{\sigma}{\policy}{\policy}
}\\
\inferrule[Triggered]{
    % M=(G,\trigger{},\enabledMap) \quad
    \enabledMap(\policy)={\sf true} \quad
    \trigger{}(\sigma)={\sf true} \quad
    \guard{G}{\sigma}{\policy}{\policy'}
}{
  \monitor{(G,\trigger{},\enabledMap)}{\sigma}{\policy}{\policy'}
}
\end{mathpar}

\Cref{subsec:formal-guardrails} provided the semantic definition for guardrails. Crucially, information about which properties to uphold, when to evaluate them, and what actions to take, must be user-specified.
This is an intentional design choice -- different policies will refer to different trigger points, use different kernel resources and notions of acceptable performance in their performance conditions, and require different types of actions to address performance violations.
Thus, users (OS operators or OS policy developers) are responsible for providing this information.
With \lang, we propose an intuitive domain-specific language that provides a small set of primitives sufficient to express a wide variety of runtime performance guardrails over kernel behavior.

Concretely, a monitor $M=((\condition{},\action{}),\trigger{},\enabledMap)$ (defined in \Cref{subsec:formal-guardrails}) is encoded in \lang using the keywords: {\sf for}, {\sf when}, {\sf check}, {\sf over}, and {\sf on_failure}.
Specifically, \lang assumes that the set of possible policies that the guardrails are supposed to monitor are distinctly named, and the action $\action{}$ switches between these named policies. \isil{The window part comes out of nowhere, since it was previously not introduced}
To specify which policies a particular monitor $M$ applies, all policies $\policy \in \policies$ for which $\enabledMap(\pi) = {\sf true}$, must be named in a list after the {\sf for} keyword.
The desired trigger points ($\trigger{}$) are specified with the {\sf when} keyword, and the performance condition $\condition{}$ is specified as a boolean predicate over various in-kernel state and observations (explained below) using the {\sf check} keyword.
\Cref{fig:gdl-grammar} shows the overall grammar of \lang.
Below, we describe the key primitives and their justification.

\paragraph{Inspection objects in the kernel.}
The performance condition, $\condition{}$ in \Cref{subsec:formal-guardrails}, operates over a finite sequence of system states, decisions, and/or events.
\lang exposes this behavior through a small set of typed inspection domains ($Domain$).
These include kernel objects (denoted {\sf KObject} in \Cref{fig:gdl-grammar}), such as pages or processes; sets of kernel objects ($Set[{\sf KObject}]$ in \Cref{fig:gdl-grammar}), which allow a guardrail to reason about collections of objects as first-class entities, e.g., whether a property holds for all memory regions of 256 contiguous pages; and instrumented kernel functions ({\sf KFunc} in \Cref{fig:gdl-grammar}), which represent decision points or result in state transformations.
\sujay{Perf metrics such as TLB misses?}
The choice of these primitives is deliberate: guardrails targeted by \lang ultimately reason about kernel objects, their collections, and the function invocations that manipulate them. By focusing the language around these domains, \lang remains narrow while still covering a broad space of runtime performance conditions.

Over these domains, operators can define observations ($Obs$ in \Cref{fig:gdl-grammar}) that extract the relevant runtime information.
This includes attributes of {\sf KObject}s (e.g., whether a page has its {\tt dirty} bit set), set-level attributes of $Set[...]$s (e.g., number of objects in the set), and decisions and execution times of instrumented kernel functions.
Any custom features that are not captured using {\sf KObject}s or {\sf KFunc}s, such as, the number of times an event occurs, can be specified via the {\sf read} operation. 
Note that guardrails are not responsible for collecting the necessary features. This is because the semantics of how to collect features correctly are unknown to the framework itself.

\lang also supports aggregation of observations ($Agg$ in \Cref{fig:gdl-grammar}) for a given element in a domain over the observation window.
This separation between inspection domains and observations is important: the former determines what objects a guardrail looks at, while the latter determines what it measures.

Finally, operators write the performance condition as predicates over these observations ($Rule$ in \Cref{fig:gdl-grammar}).
Thus, although the semantics of guardrails (in \Cref{subsec:formal-guardrails}) are defined over execution traces, \lang does not expose raw traces directly to the operator.
Instead, it provides a structured interface for expressing performance conditions concisely.

\paragraph{Trigger positions.}
As mentioned in \Cref{subsec:formal-guardrails}, a monitor is only `triggered' at user-specified points. In \lang, we support two types of trigger points that map to two common types of performance properties.
Some properties specify continuous conditions that must always hold, e.g., CPU utilization by kernel daemons should remain below a threshold, or memory fragmentation should not exceed some threshold.
Such properties are not tied to specific state transitions or events and are hence best checked at regular intervals (captured by {\sf periodic} trigger in \lang; see \Cref{fig:gdl-grammar}).
A second class of properties evaluate the correctness (or efficacy) of a particular policy decision, e.g., whether a task placement policy led to load imbalance on a NUMA system, or whether a page promotion decision by a memory tiering policy moved a cold page into hot tier.
In these cases, the natural point of evaluating the decision is when it is produced, i.e., at the invocation of the kernel function (captured by {\sf on_call} trigger in \lang; see \Cref{fig:gdl-grammar}).

There may be properties tied to higher-level events, where the state transition of interest may be missed by periodic sampling and cannot be captured cleanly by any single function invocation.
Such cases can be handled by encoding the event itself as a predicate over observations and evaluating the guardrail periodically at a sufficiently fine granularity.
The key observation is that many events of interest can be expressed as conditions over the execution trace.
Concretely, if a guardrail is intended to enforce $\condition{}$ each time an event $E$ (expression over observations) occurs, we can equivalently specify it using a monitor $M$ triggered periodically with the condition $E\implies\condition{}$. Under a sufficiently small period, $M$ will evaluate the condition $\condition{}$ exactly in cases when the event predicate $E$ holds.
